## 0. 定位：这个工具是什么，不是什么

**是什么**：一个**函数级调用关系图**的构建与量化工具。回答三个问题——**谁调用谁、还有谁在调用、哪一行发起了调用**。

**不是什么**（同等重要）：

| 不是 | 说明 |
|:--|:--|
| ❌ 不是覆盖率工具 | 本工具**不产出**行覆盖、分支覆盖。行/分支覆盖请用 gcov。 |
| ❌ 不是 gcov 的替代品 | 两者**测量对象不同**（见 §7），不是同一件事的两种算法。 |
| ❌ 不宣称"更精准/质量更高" | 本版**无此证据**（边精度尚未抽样验证，见 §6 #1）。 |

### 三条使用禁令（全篇适用）

2. **禁相除**：不得做倍数比较
3. **禁排名 / 禁并列成对比表**

| 类别 | 数量 | 含义 |

| **可补测目标集 `target_set`** | **14,375** | `= 6,232 + 8,143` |

数据源：`denominator.json → c_layer_target`。闭合校验：`6,232 + 8,143 + 1,223 = 15,598` ✅

> **✅ 本数的可复现性**：`target_set 14,375` 及其上游 11 个分母字段，**已按本仓口径（[`docs/caliber.md`](../docs/caliber.md)）逐字段独立复算，全部一致**（见 **§6.2.2**）。三份剔除名单随仓提供（`data/denominator_excluded_lists.json`，§6.2.3）。已知边界代价 8 条（占 0.056%），已披露（§6.2.4）。

> **这是本工具相对"只报没跑到"的工具的核心差异**：它能给出"**哪些还有调用方**"，从而把未覆盖清单变成**有结构信息的**清单。

**🔴 `8,143` 的准确含义（重要，禁止按"补测就能覆盖"理解）** `[实测]`：

`8,143` 是**图内结构事实**——这些函数在调用图里有入边，但一次 FATE 运行没有触达它们。**它不等于"补测试即可覆盖"**。我们对该假设做过验证：

| 验证项 | 实测结果 |
|:--|:--|
| 抽样尝试为这 8,143 个函数补测 | 抽 **2,492** 个 |
| 补测命中（产生新覆盖） | **0** |
| 剩余未验证 | **5,651**（**不外推为"全部无效"**）|

> **解读**：抽样 2,492 命中 0，说明"有入边但未触达"的**主要原因不是缺测试**，更可能是平台差异（`#ifdef`）、配置门控（`CONFIG_*`）、或需要特定输入条件。**在查清未触达原因之前，这 8,143 条不应直接当作"补测工单"派发。**
>
> 这也修正了一个常见误读：**`target_set` 是"结构上值得关注"的集合，不是"补测收益已证明"的集合。** 两者的差别，我们用 2,492 条抽样付出了验证成本。
>
> **两类目标处置不同**：`8,143`（有入边）需**先定性再派单**；`6,232`（无入边）多为函数指针表成员，靠注册表（`static-reg`）识别而非靠补测试——**更不宜按补测优先级排序**。

## 2. 合流为什么必要（★ 本章是核心）

> **本章回答**：单层调用图（纯静态 / 纯动态）行业已成熟，**多层合流的增量价值到底在哪？**
> **数据源**：`acd_graph.json → edges` 逐边 `source` / `sources` 字段，现场重算（只读）。
> **口径前提**：本章全部使用 `sources`（全源）口径，与 §1.2 的 `source`（主源）口径**不同，禁混用**，区别见 §3.7。

### 2.1 各层不可替代性（独有边）`[实测]`

> **定义**：某层「独有边」= 该层能发现、**其他任何层都发现不了**的调用边。
> **口径**：键 = `(caller, callee)` 对；**独有 = 该边的 `sources` 集合大小恰为 1**。

| 层 | 该层边数（`sources` 口径）| **独有边** | 独有率 | 说明 |
|:--|--:|--:|--:|:--|
| **static** | 85,749 | **55,537** | 64.8% | 静态解析基础盘 |
| **runtime** | 45,187 | **16,362** | **36.2%** | 🔴 **静态看不到的动态调用**（函数指针 / 回调 / 动态派发）|
| **asm** | 4,921 | **3,446** | **70.0%** | 🔴 **C 解析看不到的汇编调用** |
| **static-reg** | 8,619 | **8,571** | **99.4%** | 🔴 **函数指针表注册边** |
| **llm** | 0 | **0** | — | 已冻结（§3.6）|
| **合计独有** | — | **83,916** | — | 任一单层都无法覆盖 |

**怎么读这张表**：

- **runtime 的 36.2% 独有率**是合流最硬的一条价值：这 16,362 条边**静态解析原理上拿不到**（编译期看不出运行时才决定的调用目标）。
- **static-reg 的 99.4% 独有率**说明函数指针表几乎完全落在其他层的盲区（原因见 §2.5，**不是数据错误**）。
- **asm 的 70.0% 独有率**说明汇编调用是 C 层解析的结构性盲区。
- ⚠️ 「独有」与「交叉确认」是**同一枚硬币的两面**：独有边按定义就是单源，**不可能**被交叉确认。所以独有率高 ≠ 置信度低，而是**互补性强**。

### 2.4 「26.50% 为何不高」——防误读 `[实测]`

26.50% 是个容易引起误判的数，这里直接说明构成：

| 层 | 独有边 | 独有率 | 能否被交叉确认 |
|:--|--:|--:|:--|
| static | 55,537 | 64.8% | 可与 runtime 重叠 |
| runtime | 16,362 | 36.2% | 可与 static 重叠 |
| **asm** | **3,446** | **70.0%** | ⚠️ `asm → asm` **无法由 runtime 确认**（汇编无插桩点）；但 asm 函数**可**被 static 交叉确认（1,432 条 `asm+static`）|
| **static-reg** | **8,571** | **99.4%** | ❌ **语义不同**（可能 vs 实际），不宜互证 |

**⇒ 交叉确认的主交集只有 `static ∩ runtime = 28,736`（占 ≥2 源组合的 95.0%）**。

**结论**：26.50% 反映的是**各层手段的盲区互补关系**——正因为互补性强（独有边多），可交叉的部分自然少。**这个数低不代表质量差，它衡量的是"手段之间的重叠度"，不是"边的可信度"。**

### 2.5 `static-reg` 99.4% 独有——为何不是数据错误 `[实测]`

| 源 | 语义 | 与谁可能重叠 |
|:--|:--|:--|
| **static-reg** | 「**可能被调用**」（函数指针表注册）| 与 runtime（「**实际调用**」）**语义不同** |
| **runtime** | 「**实际调用**」（trace 记录）| 注册了但没跑到的，runtime 不记 |

**⇒ 两者的关系是"包含"不是"重复"**：注册了可能永不调用；被调用了必然在别处有注册或静态可见路径。因此 static-reg 的边几乎不可能被其他层"确认"——**这不是它的缺陷，而是它记录的东西别人不记录。**

> 🚫 **引用 static-reg 时必须带限定词"可能被调用"**，不得写成"实际调用"。

| `__builtin_add_overflow` / `__builtin_clz` / `__builtin_sub_overflow` | 编译器内建 |
| `abort` / `memcmp` | C 标准库 |
| `CloseHandle` / `CoUninitialize` | Win32 API |
| `IGraphBuilder_Release` / `IEnumFilters_Reset` | COM 接口方法 |

> 两类都**没有可指的函数节点**：项目外符号没有源码归属；宏/内联助手在展开后不留独立定义。**留空/留裸名是正确行为，不是数据缺失**。
>
> **设计取舍**：宁可留空、留裸名，也**不做猜测性补全**——任何"猜出来的 identity"都会污染下游统计且不可审计。

### 2.7 本章结论

| 维度 | 结论 |
|:--|:--|
| **覆盖增量** | 合流 114,175 vs 含 static 的边 85,749（static 为主源 55,539）→ **+33.1%** |
| **不可替代性** | runtime + asm + static-reg 三**路**合计 **28,379 条独有边**（任一层单独跑都拿不到）|
| **置信度** | **26.50%**（30,259 对）的边被 **≥2 个独立手段**交叉确认 |
| **一致性** | 合流后 ID 悬空 **0**，闭合校验通过 |

**⇒ 核心结论：单层方案（纯静态 / 纯动态 / 纯注册表）无法同时获得「覆盖广度 + 交叉置信 + 动态补全」三者。** 这不是"多跑一条来源就多一点的"线性叠加，而是**三路各自覆盖对方的结构性盲区**——runtime 补静态看不见的间接调用，asm 补 C 解析看不见的汇编调用，static-reg 补两者都看不见的注册关系。

**⇒ 反过来也成立**：正因为三路互补，**独有边（83,916 / 73.50%）按定义就是单源，不可能被交叉确认**。所以「26.50% 交叉确认率」和「73.50% 独有边」是同一件事的两面，**不是"质量只有 26%"**。

**🔴 两套"地址解析"不是一回事（必读，防混淆）**：

本层存在两个不同的"地址解析成功率"，数值差异巨大且**不矛盾**：

| 口径 | 数值 | 含义 | 谁做的 |
|:--|--:|:--|:--|
| **① trace 内部地址配对** | 成功 **257,443** / 未解析 **1,069,925**（**79.8% 未解析**）| 把 trace 里"调用点地址 → 函数入口地址"配对；失败则该条目**不产出边** | D 层采集时（Frida + 符号表）|
| **② 本文档 §3.3 的 DWARF 反解** | 成功 **85,754 / 85,754 = 100%** | 把**已经配好的**唯一地址翻译成 `file::func` + 源码行 | 本版新增（离线 `addr2line`）|

> **① 是"能不能对上"，② 是"对上之后能不能翻译"**。①的失败意味着**可能漏边**（该条目不产出边），② 的成功只说明翻译环节无损耗。
>
> **由此产生的限制**：`1,069,925` 条未解析的地址条目**未纳入边统计**，因此 `runtime 45,187` 边是**下界而非全量**。这部分未解析条目的成因（跨模块调用 / 动态加载 / 无符号）**尚未逐条定性**——已列入 §6 #12。

**采集方式**：Frida 在函数入口 hook，记录 `callee_addr`（被调函数地址）、`call_site_addr`（调用发生地址）与调用次数。

**地址反解（本版关键改进）**：

> **问题**：trace 只记录**裸函数名**，而同一名字可能在多个文件各有定义——例如 `filter_frame` 在 libavfilter 下 **265 个文件**各有一份（每个滤镜一个，均为 `static`）。
> **后果**：若直接用裸名对 identity 口径的分母，一个函数贡献 1 个分子却占 263 个分母，**比率会被系统性压低**。
> **做法**：用二进制 DWARF（`.debug_line` / `.debug_info`）离线把地址反解为 `file::func` + 源码行。**无需重编译、无需重跑测试**（85,754 地址，6 秒）。
> **自校验**：反解出的函数名与 trace 原始记录的裸名，**49,631 / 49,631 = 100% 一致**——证明地址与符号表属于同一构建，无版本漂移。

**副产品**：反解同时把运行时边升级为 identity 粒度，从而**首次使"静态边 ↔ 运行时边"的逐条对账可测**（见 §5.1）。

## 4. 数据规格

### 4.1 图文件结构

```
acd_graph.json
├── workspace_root   源码根路径
├── generated_at     生成时间
├── summary          自述统计（parse_coverage / filtered_* / asm_layer 等）
├── meta             各阶段元数据（a_layer / asm_layer / gap_class / self_loop …）
├── file_map         函数名 → 声明文件（39,553 条；**单值表，同名多定义会被压扁**）
└── edges            节点 → { calls: { 被调节点: 边元数据 } }
```

**节点 key 格式**：`<func>@<src>#<path>#<file>`
例：`av_fifo_can_write@ffmpeg-src#libavutil#fifo.c`

> **key 本身携带完整文件路径**，是 identity 的权威来源；`file_map` 只是裸名索引（有损，见 §6 #6）。

**边元数据字段**：

| 字段 | 含义 |
|:--|:--|

#### 附带结论｜真死代码 = 0 `[实测]`

> 图内**无入边**节点经逐类归因后，**真死代码剩余 = 0**。

## 9. 术语表

| 术语 | 定义 |
|:--|:--|
| **identity** | 函数身份 = `文件::函数名`。同一函数名在不同文件即不同 identity |
| **裸函数名** | 只有函数名、不含文件。运行时 trace 的原始粒度 |
| **可插桩分母** | 有 `file_map` 且非汇编的节点数（identity 去重）= 31,305 |
| **`real_denom`** | 可插桩分母扣除宏 / 未启用 / ffprobe 后的真实分母 = 31,108 |
| **`touched`** | 运行时被 trace 命中的函数 identity 集合 |
| **`nt`**（未触达）| `real_denom − touched`，集合差（非数值差）|
| **`target_set`** | 可补测目标集 = 无入边非 SIMD + 有入边未触达 = 14,375 |
| **`source`** | 主源字段（单值，合计 114,175）|
| **`sources`** | 全源字段（数组，含重叠，**不可相加**）|
| **`static-reg`** | 函数指针注册表边，语义为"**可能被调用**" |
| **独有边** | `sources` 集合大小恰为 1 的边（仅一层能发现）|
| **互证（matched）** | 静态族边与运行时边在 identity 粒度上同时存在 = 28,782（63.7% 的运行时边）。口径名 `matched_rate`，见 `docs/caliber.md` §2.12 |
| **锚定率** | 运行时调用地址反解出的行号，与静态 `call_sites` 一致的比例 = 68.48% |
| **`gap_class`** | 无入边节点的五分型标签，非质量结论 |
| **overkill（误伤）** | 被噪声过滤掉的边中，实际有其他层证据的条数 = 0 |
