## The 30-second version

This is a call graph of **FFmpeg 9.1-dev** (`n9.1-dev-1030-g818cecc6`, MinGW-w64 / x86_64) —
2,257 translation units, 31,500 functions, 7,420 assembly functions, **114,175 call edges**.
Edges are fused from four sources: static parsing (including macro expansion), runtime
instrumentation, assembly (source + disassembly), and function-pointer registry analysis.

The claim we deliberately avoid: the strongest single source already reaches **75.1%**
(85,749 edges); the remaining **24.9%** (28,426 edges) is what no single source can produce.
**30,259 edges (26.50%)** are independently confirmed by two or more sources.

Edge, node and source counts are recomputable from the shipped artifact; **reach and anchor rates are not** — they need three extra artifacts that are not shipped (see `docs/caliber.en.md` §2.7). The parts we did not reach are published next to the parts we did. About 2 MB of repository excluding the release zip; nothing to install — one HTML file opens in a browser.

---

## 1. What is different here

Four things, all checkable inside the repository:

1. **One number, one definition** — [`docs/caliber.en.md`](docs/caliber.en.md), deliberately without a
   numeric table; numbers live in `data/denominator.json`.
2. **The checks can fail** — `scripts/verify_graph.py` scores **14/16 FAIL** when pointed at an
   older graph. A suite that always passes is not a suite.
3. **The gaps are public** — 13,277 functions with no inbound edge, attributed in five classes;
   `DEAD_SUSPECT` is *suspected*, never "dead code".
4. **Per-edge provenance expands** — click a node in the viewer and each edge shows which sources
   saw it independently, plus call-site lines and `trace_count`.

We do not claim "more accurate": edge-level precision / recall are **unmeasured** (report §6 #1).
The comparison to existing tools is about evidence structure, not accuracy.

## 2. The numbers

| Item | Value |
|---|---:|
| Caller nodes | **38,697** |
| Edges | **114,175** |
| Strongest single source (`sources` contains `static`) | **85,749 = 75.1%** |
| What no single source can produce | **28,426 = 24.9%** |
| Edges confirmed by ≥2 independent sources | **30,259 = 26.50%** |
| Function reach (`touched / instrumentable`) | **49.74%** (15,571 / 31,305) |

We do not say "+33.1%": that is just 28,426 ÷ 85,749 arithmetic, and it makes a structural
result sound like a product upgrade. The honest sentence is: the single-source ceiling is 75%,
and the whole value of fusion sits in the last quarter.

Two numbers that look contradictory and are not: **28,426** = edges whose `sources` exclude
`static`; **28,379** = edges seen by exactly one of runtime / asm / registry (the Chinese guide
quotes this one for "no single source can produce"). The 47-edge difference is pairs of
non-static sources, e.g. runtime + static-reg.

Function **reach** is not "coverage": it is neither line nor branch coverage, and reusing the
word invites a wrong comparison with gcov.

## 3. Why this library is a hard sample

| Difficulty | Why a single source misses it |
|---|---|
| Function-pointer registries | codecs and filters are attached through struct tables; static parsing sees the field read, not the final callee |
| Macros + template instantiation | DSP paths are generated by `#include` templates and macros — the functions exist only after expansion |
| x86 assembly mixed in | a C-side parser simply skips `.asm` / `.S` files |
| Same-name `static` definitions | `filter_frame` exists **263** times in different files; a bare name is one-to-many |

That is why 75.1% is not "half done" — it is the ceiling that this codebase's shape imposes on
any single technique.

## 4. What the gaps look like

Every caller node carries a `gap_class`. Five classes, summing to 38,697 nodes:

| Class | Count | Meaning |
|---|---:|---|
| `HAS_INBOUND` | 25,420 | someone calls it |
| `UNKNOWN_ASM` | 4,572 | assembly-side, unresolved |
| `UNKNOWN_DYNAMIC` | 3,611 | reached only through dynamics we did not resolve |
| `DEAD_SUSPECT` | 2,650 | no inbound, mapped, non-asm, DSP-shaped — **suspected only** |
| `NO_FILE_MAP` | 2,444 | no file mapping |

The last four total **13,277** nodes with no inbound edge. They are drawn in the viewer, not
filtered out. "DEAD_SUSPECT" is a suspicion, not a verdict.

## 5. What you can actually do with it

| Want | Use | Size |
|---|---|---|
| Fill test coverage | `target_set.json` — untouched and instrumentable, SIMD removed | **14,375** |
| Find likely unreachable functions (suspected only) | `gap_class = DEAD_SUSPECT` | **2,650** (suspected, never "dead code") |
| Find dynamic calls | `source = static-reg` | **8,571**, all low confidence — "possible", not "happened" |
| Jump to a source line | per-edge `call_sites` | 69.96% of static edges carry one |

Confidence tiers are explicit: high / medium / low. `static-reg` edges are low and must be
quoted as possibility only.

## 6. What we did not do

- Function reach **49.74%** — structural: functions never executed by the FATE run cannot be reached.
- Line-level anchoring **68.48%** — depends on runtime traces and a DWARF binary; **not** recomputable
  from the shipped graph.
- C layer (LLM-inferred pointer tables) — implemented, verified, then **frozen at 0 edges**.
- Empirical scope: **one** sample. FFmpeg 9.1-dev / MinGW-w64 / x86_64. No claim about other projects.

A call graph that claims full coverage is usually one that did not draw its gaps.

## 7. What is open, what is not

- **Open**: the method, this 114,175-edge graph, the viewer, the verifiers, the metric definitions.
- **Not open**: the engine and the day-to-day workflow that turns "3.3–3.6 hours per FFmpeg run"
  into "query your own repository whenever you want".
- Product-side material is labelled separately and is **not** part of this repository's evidence.
  The build engine is not included: this repository ships data, methodology and verifiers, not a
  tool that builds graphs for arbitrary projects.

**Product side (labelled separately, not evidence).** **Mingjian AOS is an Agent OS**: it manages five
things — tool bus, permissions, tasks, long-term memory, and a personal gateway that runs on your
own machine (the single egress for models and capabilities; permissions, write-guards and cost all
land there). It ships no model, and it is not an IDE. The **ACD engine** is one module of it;
C/C++ is one deeply adapted line inside that module, and FFmpeg is the stress sample, not the
boundary. What this repository can prove is exactly this graph and the checks around it — nothing
beyond.

- **Pull requests**: not accepted at this stage — open an issue first.

## 8. Three things worth attacking first

1. **Why do 85,749 and 55,539 differ?** — "edges whose `sources` contain `static`" vs "edges whose
   primary source is `static`". See the definitions in [`docs/caliber.en.md`](docs/caliber.en.md).
2. **Isn't a 26.50% cross-confirmation rate low?** — the other 73.50% are single-source edges; by
   definition they cannot be cross-confirmed. Same fact, two sides.
3. **Can 49.74% be called coverage?** — no. This repository only uses **function reach**
   (`touched / instrumentable`).

## Getting started (30 seconds)

1. Open [`viewer/acd-viewer.html`](viewer/acd-viewer.html) — three views, fully offline. Click a
   node: the right pane shows which sources saw each edge, call-site lines, `trace_count`.
2. Open [`release/MANIFEST.txt`](release/MANIFEST.txt) — bytes and md5 for graph, denominator, target set.
3. Query a function without unzipping the 101 MB graph:

```bash
python scripts/query.py --callees av_make_error_string
python scripts/query.py --callers filter_frame      # 263 same-name ids, listed, never merged
python scripts/query.py --selfcheck                 # 114,175 edges / 38,697 caller keys
```

> The zip is **not** in git — download it from Releases into `release/` first.
